> **لوحة تحكم الإدارة المركزية المستقلة لنظام Compu MSS**  
> مصممة للنشر السحابي (Serverless / Vercel) والاتصال بقاعدة بيانات Supabase، مع عزل كامل عن تطبيق سطح المكتب وعن بيانات الإكسسوارات المحلية.


### الأهداف الأساسية المنجزة:
- **المرحلة 1:** تأسيس هيكل لوحة التحكم، الربط السحابي، الفروع والمخازن، سجل التدقيق المحمي، واستعراض المخزون.
- **المرحلة 2 (الحالية):** إدارة مستخدمي الفروع بالكامل، تشفير وتعيين رموز الدخول (Bcrypt)، تعيين صلاحيات الوحدات (`accessories` / `mss` / `both`)، إدارة إصدارات الأمان (`credential_version` و `permission_version`)، إبطال الجلسات المركزية، وتأسيس عقد المصادقة لتطبيق سطح المكتب في المرحلة 3.

## 3. الأقسام الرئيسية للوحة التحكم (Navigation Sections)

1. **نظرة عامة (Overview):** مؤشرات الأداء الحيوية (إجمالي الحسابات، الفروع النشطة، توزيع الصلاحيات، وآخر الأحداث الإدارية).
2. **إدارة المستخدمين (Users Management - المرحلة 2):**
   - استعراض الحسابات مع البحث الفوري بالاسم واسم المستخدم.
   - تصفية متقدمة حسب: الصلاحية (`both` / `accessories` / `mss`)، الفرع/المخزن، والحالة (نشط / معطل).
   - نافذة إنشاء مستخدم جديد مع تأكيد رمز الدخول واختيار الصلاحيات وتعيين الفروع المتعددة.
   - نافذة تعديل بيانات المستخدم وصلاحياته.
   - نافذة منفصلة لتغيير وتشفير رمز الدخول تضمن زيادة `credential_version` وإبطال الجلسات السابقة.
   - نافذة تأكيد تعطيل الحساب مع توضيح إبطال كافة الجلسات النشطة.
   - زر مخصص لإبطال جلسات المستخدم يدوياً (Revoke Active Sessions).
   - شارات إصدارات الأمان: `v[cred].[perm]`.
3. **الفروع والمخازن (Stores & Warehouses):** إنشاء وتعديل الفروع والمخازن، تفعيل/تعطيل الوحدات مع الحفظ التاريخي الكامل.
4. **المخزون المشترك (Inventory Foundation):** استعراض أولي للقراءة فقط لكتالوج الموديلات وحالة الأجهزة في السحابة.
5. **تحويلات المخزون (Inventory Transfers):** مساحة محجوزة بوضوح للمرحلة الخامسة (Phase 5) وفق قواعد المشروع الصارمة.
6. **سجل النشاط والتدقيق (Activity & Audit Log):** سجل شامل ومحمي لجميع العمليات الإدارية الحساسة، مع إمكانية البحث وعرض التفاصيل التقنية.
7. **إعدادات النظام والأمان (System Settings):** حالة الربط، تأكيد قواعد العزل المعماري، ومعلومات النسخة والتطوير.

## 4. نموذج بيانات حسابات المستخدمين (User Account Model)

جدول `app_users` في قاعدة البيانات السحابية يشتمل على الحقول التالية:
- `id` (UUID - المفتاح الأساسي الثابت).
- `username` (اسم المستخدم الفريد والمطبع).
- `display_name` (الاسم المعروض الكامل للموظف/المحاسب).
- `access_code_hash` (الرمز السري مشفر بخوارزمية Bcrypt - لا يعاد للواجهة أبداً).
- `allowed_modules` (`accessories` / `mss` / `both`).
- `default_store_id` (الفرع الافتراضي المرتبط).
- `credential_version` (إصدار الاعتماد الأمني - يزداد عند تغيير الرمز أو التعطيل لإبطال الجلسات).
- `permission_version` (إصدار الصلاحيات - يزداد عند تغيير الصلاحيات لتحديثها فوراً عند اتصال التطبيق).
- `is_active` (حالة الحساب - عند التعطيل يُحظر الدخول وتلغى الجلسات).
- `last_login_at` (تاريخ ووقت آخر تسجيل دخول ناجح).
- `created_at` و `updated_at`.

### جدول جلسات سطح المكتب (`app_user_sessions`):
- `id` (UUID).
- `user_id` (UUID - مفتاح أجنبي يربط بالمستخدم).
- `session_token_hash` (تجزئة SHA-256 لرمز الجلسة).
- `credential_version` و `permission_version` (لمقارنتها مع إصدار المستخدم وإبطال الجلسة عند عدم التطابق).
- `device_info` (معلومات جهاز سطح المكتب المصرح له).
- `expires_at` (تاريخ انتهاء صلاحية الجلسة - افتراضياً 30 يوماً).
- `revoked_at` (تاريخ ووقت الإبطال - إذا لم يكن خاوياً تعتبر الجلسة ملغاة).
- `created_at`.

## 5. سياسات الأمان والتشفير (Security Architecture)

### أ. تطبيع أسماء المستخدمين (Username Normalization):
- يتم تطبيع اسم المستخدم تلقائياً بقصه وتحويله إلى أحرف صغيرة خالية من الفراغات (`lower(trim(username))`).
- التحقق الإلزامي من ألا يقل الاسم عن 3 أحرف وألا يحتوي على رموز غير مسموح بها.
- ضمان عدم تكرار أسماء المستخدمين على مستوى قيود قاعدة البيانات (`UNIQUE`).

### ب. تشفير رموز الدخول (Access Code Hashing):
- تشفير من طرف الخادم بنسبة 100% باستخدام خوارزمية **Bcrypt** بـ 10 جولات تمليح (Salt Rounds = 10).
- لا يتم حفظ الرمز كنص صريح إطلاقاً في أي جدول أو سجل تدقيق أو متغير بيئة.
- لا يتم إرجاع الهاش أو كشفه للواجهة الأمامية؛ دالة `sanitizeUser` تحذف الحقل تلقائياً قبل الرد.
- الحد الأدنى لطول الرمز 4 خانات، مع إلزامية مطابقة تأكيد الرمز في واجهات الإنشاء والتغيير.

### ج. الحماية ضد هجمات التخمين (Rate Limiting & Lockout):
- تعقب تلقائي للمحاولات الخاطئة لكل اسم مستخدم/IP.
- عند بلوغ 5 محاولات خاطئة متتالية يتم قفل المصادقة مؤقتاً لمدة 15 دقيقة (`BLOCK_DURATION_MS = 15 mins`).
- رسائل الخطأ عامة وموحدة: `"بيانات الدخول غير صحيحة أو الحساب معطل"` دون الكشف عما إذا كان اسم المستخدم موجوداً في النظام.

## المرحلة 3: مصادقة سطح المكتب، الجلسات الآمنة والترخيص أوفلاين (Phase 3)

تم ربط وتكامل تطبيق سطح المكتب (Tauri v2 + React 19) مع نظام المصادقة والصلاحيات المدار عبر لوحة التحكم:

### 1. معمارية المصادقة والجلسات (Authentication Architecture)
- **واجهة تسجيل الدخول (Login Screen):**
  - تصميم Dark-first باللون الأزرق المعتمد للعلامة التجارية متوافق مع معايير Unslop.
  - حقول اسم المستخدم ورمز الدخول مع خيار إظهار/إخفاء الرمز.
  - رسائل خطأ موحدة غير كاشفة لمنع هجمات الاستكشاف.
  - تنظيف فوري للحقول الحساسة عند الفشل أو النجاح مع حظر هجمات التخمين.
- **التخزين الآمن محلياً (Windows DPAPI):**
  - لا يتم تخزين التوكنات إطلاقاً في `localStorage` أو ملفات JSON غير مشفرة أو أعمدة SQLite عادية.
  - تشفير الجلسة باستخدام **Windows Data Protection API (DPAPI)** عبر أوامر Tauri في Rust (`save_secure_session`, `load_secure_session`, `clear_secure_session`).
  - يتم تمرير البيانات عبر Stdin لمنع ظهورها في قائمة العمليات (Task Manager / Process Monitor).

### 2. سياسة العمل بدون اتصال بالإنترنت (Offline Authorization Policy)
- **النافذة الزمنية الافتراضية:** 7 أيام منذ آخر تحقق ناجح عبر الإنترنت (`lastOnlineValidationAt`).
- **فحص مكافحة التلاعب بالساعة (Anti-tampering Clock Rollback):**
  - في حال إرجاع تاريخ وساعة الجهاز إلى الماضي بأكثر من دقيقة واحدة، يتم إيقاف الجلسة ومطالبة المستخدم بالاتصال بالإنترنت لإعادة المصادقة.
- **انتهاء المهلة:**
  - عند تجاوز 7 أيام، تظهر رسالة انتهاء الصلاحية أوفلاين وتتوقف الواجهات المحمية.
  - **الحفاظ التام على البيانات:** لا يتم حذف أو تصفير أي سجلات أعمال محلية أو سجلات Outbox معلقة.

### 3. إعادة الاتصال والتحقق التلقائي (Reconnection & Auto-Revalidation)
- عند عودة اتصال الإنترنت:
  - **الحالة أ (لا تغيير):** استمرار العمل وتحديث ختم التحقق.
  - **الحالة ب (تعديل الصلاحيات):** تحديث الصلاحيات فورياً، وتحويل المستخدم تلقائياً للقسم المصرح له ومنع الأقسام المحظورة.
  - **الحالة ج (تعطيل الحساب):** إبطال الجلسة وتوجيه المستخدم لشاشة تسجيل الدخول مع الحفاظ على البيانات.
  - **الحالة د (تغيير الرمز):** اكتشاف اختلاف `credential_version` وطلب إدخال الرمز الجديد.
  - **الحالة هـ (إبطال الجلسة):** تسجيل الخروج وتوجيه المستخدم لشاشة الدخول.
  - **الحالة و (انقطاع الخادم المؤقت):** تطبيق سياسة الأوفلاين دون افتراض تعطيل الحساب.

### 4. حماية المزامنة في الخلفية (Background Sync Safety)
- التحقق الإلزامي من وجود جلسة صالحة وصلاحية `mss` قبل تنفيذ أي عمليات سحابية في محرك المزامنة `mssSyncService`.
- الحفاظ على العمليات المعلقة في Outbox دون حذفها أو تزييف هويتها إذا كان الحساب غير مفعل أو مخصص لـ Accessories فقط.

### 5. مسار الترحيل (SQL Migration)
```text
supabase/migrations/20261117_phase03_desktop_auth.sql
```
يحتوي على:
- دالة `revalidate_desktop_session` للفحص الذري للجلسة عبر السيرفر.
- دالة `revoke_desktop_session` للإبطال الفوري للتوكن.
- عمود `last_active_at` وفهارسه.

## المرحلة 4: إدارة الفروع والمخازن والشركاء (Phase 4: Stores, Warehouses & Partners)

تم الانتهاء من بناء نظام متكامل لإدارة الهيكل التنظيمي والمواقع الجغرافية في لوحة تحكم الإدارة:

### 1. النموذج البياني للمواقع (Location Data Model)
- يدعم الجدول `system_stores` الآن ثلاثة أنواع من المواقع:
  - `store` (محل تجزئة / نقطة بيع).
  - `warehouse` (مخزن بضائع رئيسي / فرعي).
  - `combined` (منشأة مدمجة تجمع بين نقطة بيع ومخزن).
- إضافة حقول التتبع والأرشفة الآمنة:
  - `description` (وصف وتفاصيل الموقع).
  - `is_archived` (علامة الأرشفة المنطقية / Soft-delete).
  - `archived_at` (تاريخ ووقت الأرشفة).
  - `merged_into_id` (معرف الفرع الوجهة في حال الدمج لتتبع الأنساب التاريخية).

### 2. القاعدة المعمارية الصارمة: "المستخدمون ليسوا مخازن" (Users Are Not Warehouses)
- ملكية المخزون والأجهزة مرتبطة فيزيائياً بالمواقع الجغرافية (`system_stores.id` و `stock_location`) وليست مرتبطة بهويات الشركاء أو حسابات المحاسبين.
- عند انضمام شريك، نقله بين الفروع، أو إنهاء شراكته، **لا يتم أبداً حذف أو تعديل أو إعادة كتابة أي فواتير، مبيعات، أو سجلات أجهزة تاريخية**.

### 3. إدارة عضويات الشركاء والفروع (Partner & Store Memberships)
- الربط متعدد-إلى-متعدد (`user_store_assignments`):
  - يمكن للموقع الواحد أن يضم عدة شركاء/محاسبين.
  - يمكن للمستخدم الواحد أن يكون مصرحاً له بالوصول إلى عدة مواقع.
  - تحديد الفرع الافتراضي (`is_default_store`).
- عند إضافة أو إزالة شريك من فرع:
  - يتم تحديث `permission_version` للمستخدم تلقائياً.
  - يؤدي ذلك فورياً إلى إعادة فحص وتحديث الصلاحيات في تطبيق سطح المكتب عند اتصاله بالإنترنت.

### 4. معالج دمج الفروع الآمن خماسي الخطوات (Safe 5-Step Store Merge Wizard)
تمت معالجة السيناريو الحرج (دمج عدة فروع سابقة مثل "محل 1" و "محل 2" في كيان واحد):
- **الخطوة 1 (اختيار الفروع المصدر):** اختيار فرعين نشطين أو أكثر لدمجها.
- **الخطوة 2 (اختيار الفرع الوجهة):** اختيار فرع قائم أو إنشاء موقع مدمج جديد.
- **الخطوة 3 (معاينة الأثر التاريخي):** فحص المستخدمين المتأثرين، عدد الأجهزة في كل موقع، والتأكيد على حماية السجلات التاريخية.
- **الخطوة 4 (تأكيد المسؤولية):** إقرار صريح عبر خانة اختيار بإدراك أن العملية غير قابلة للتراجع.
- **الخطوة 5 (التنفيذ الذري عبر RPC):**
  - أرشفة الفروع المصدر وتعيين `is_archived = true` و `merged_into_id`.
  - إعادة تعيين الشركاء والمحاسبين للفرع الوجهة تلقائياً وزيادة `permission_version`.
  - تسجيل حدث تدقيق آمن في `admin_audit_logs`.
  - **حظر تام لنقل المخزون في المرحلة 4:** تبقى جميع الأجهزة مسجلة بمواقعها الأصلية دون تحريك أي كميات أو أرقام تسلسلية (المخزون محجوز للمرحلة 5).

### 5. ملف الترحيل وقاعدة البيانات (SQL Migration)
```text
supabase/migrations/20261117_phase04_stores_and_partners.sql
```
يحتوي على:
- تعديل قيد التحقق `check_store_type` ليشمل `combined`.
- إضافة أعمدة الأرشفة ونسب الدمج.
- إنشاء جدول تتبع عمليات الدمج `store_merges`.
- دالة `execute_store_merge` الذرية على مستوى السيرفر (Atomic Server RPC) لضمان عدم حدوث حالات عدم اتساق.

# المرحلة 5: إدارة المخزون وتحويلات الأجهزة والمزامنة الحية (Phase 5: Inventory Transfers & Concurrency)

تم تنفيذ وتفعيل نظام تحويلات المخزون المركزي الشامل داخل لوحة تحكم المسؤول المستقلة (`admin-dashboard/`) مع الحفاظ التام على سلامة البيانات والقيود المالية، ودون المساس بقاعدة بيانات قسم الإكسسوارات المحلية (Rule 6).

## 1. نموذج ملكية المخزون (Inventory Ownership Model)

- **القاعدة (A):** لكل جهاز فعلي موقع حالي واحد موثوق ورسمي (`stock_location`).
- **القاعدة (B): "المستخدمون ليسوا مخازن" (Users Are Not Warehouses):** ملكية الأجهزة والمخزون تتبع دائماً المواقع الجغرافية/المنطقية للفروع والمخازن (`system_stores`)، ولا ترتبط مطلقاً بحسابات المستخدمين أو الكاشير.
- **القاعدة (C): ثبات السجلات المالية والتاريخية (Historical Records Immutability):** حركة تحويل المخزون تأخذ لقطة دقيقة لسعر الشراء الأصلي (`purchase_cost_snapshot`) وتوثقه في سجل التحويل دون تعديل سعر الشراء التاريخي أو التأثير على فواتير الشراء القديمة.
- **القاعدة (D): التحويل ليس بيعاً ولا شراءً (Transfer is Neither Sale nor Purchase):** لا تصدر فواتير مبيعات أو مشتريات عن التحويلات، ولا تنشأ أرباح أو إيرادات وهمية، ويظل إجمالي المخزون المالي والكمي للشركة ثابتاً تماماً (قانون حفظ المخزون).
- **القاعدة (E): عزل نظام الإكسسوارات (Rule 6 Separation):** كافة تحويلات المخزون تنفذ حصراً على أجهزة Compu MSS المسلسلة. قاعدة بيانات SQLite المحلية الخاصة بالإكسسوارات تظل معزولة تماماً وغير متصلة بالتحويلات السحابية.

## 2. نموذج المخزون المسلسل وأنواع التحويلات (Transfer Types)

نظام Compu MSS يعتمد بنية مسلسلة بالكامل (`mss_devices`) حيث يملك كل جهاز رقماً تسلسلياً فريداً (`serial_number`). تدعم لوحة الإدارة 4 أنواع للتحويل:

1. **التحويل الفردي (Individual Device Transfer):** نقل جهاز واحد برقم السيريال أو المعرف الفريد.
2. **التحويل المتعدد المحدد (Selected Devices Transfer):** تحديد مجموعة أجهزة دفعة واحدة ونقلها ذرّياً (All-or-Nothing).
3. **تحويل مجموعة الموديل (Product Group Transfer):** تحديد موديل معين ونقل عدد محدد من الأجهزة المسلسلة المتاحة التابعة له.
4. **تحويل كامل المخزون المؤهل (Transfer All Eligible Inventory):** نقل كافة الأجهزة المتوفرة المسموح بنقلها من موقع المصدر إلى الوجهة بعد مراجعة الاستثناءات والأسباب.

## 3. قواعد أهلية الأجهزة للنقل (Device Eligibility Rules)

- **الأجهزة المؤهلة (`isEligibleForTransfer = true`):**
  - الأجهزة ذات الحالة `AVAILABLE` والموجودة فعلياً في موقع المصدر المحدد.
- **الأجهزة المستبعدة وغير المؤهلة (`isEligibleForTransfer = false`):**
  - `SOLD`: تم بيع الجهاز وتسجيل فاتورته الرسمية (لا يجوز نقله).
  - `RESERVED`: الجهاز محجوز لعميل حالياً (لا يجوز نقله).
  - `MAINTENANCE`: الجهاز قيد الصيانة والإصلاح الفني.
  - `RETURNED`: جهاز مرتجع قيد الفحص والاعتماد.

## 4. مسار معالج التحويل الإرشادي خماسي الخطوات (Guided Transfer Wizard)

يوفر المكون `TransferWizardModal.tsx` تدفقاً تفاعلياً آمناً:
1. **الخطوة 1: تحديد موقع المصدر:** اختيار الفرع/المخزن الذي ستخرج منه الأجهزة.
2. **الخطوة 2: تحديد موقع الوجهة:** اختيار الفرع/المخزن المستلم (مع منع اختيار نفس المصدر).
3. **الخطوة 3: تحديد النطاق والأجهزة:** اختيار فردي، متعدد، حسب الموديل، أو كل المؤهل، مع عدادات فورية وإشارات بصرية للأجهزة المستبعدة.
4. **الخطوة 4: معاينة الأثر والتحقق المسبق:** استعراض الأجهزة المؤهلة وقيمتها الشرائية الإجمالية، وبيان تفصيلي بالأجهزة المستثناة مع سبب المنع باللغة العربية.
5. **الخطوة 5: التأكيد والإقرار:** إقرار صريح بعدم التراجع، وملاحظات إدارية، وحماية تلقائية من النقر المزدوج عبر مفتاح فريد لمنع التكرار (`Idempotency Key`).
6. **الخطوة 6: نتيجة التنفيذ:** عرض الرقم المرجعي للتحويل (`TRF-YYYYMMDD-XXXX`) مع رابط فوري لمعاينة السجل التفصيلي.

## 5. التنفيذ الذري وحماية التكرار (Atomicity & Idempotency)

- دالة قاعدة البيانات `execute_inventory_transfer` تعمل كمعاملة ذرية واحدة (`SECURITY DEFINER`):
  - التحقق المسبق من وجود الأجهزة في المصدر وأهليتها (`AVAILABLE`).
  - في حال عدم أهلية أي جهاز، يتم التراجع عن العملية بالكامل (Rollback) لمنع التحويل الجزئي غير المتوقع.
  - إنشاء سجل رئيسي في جدول `inventory_transfers`.
  - أخذ لقطات تفصيلية لكل جهاز في `inventory_transfer_items`.
  - تحديث موقع الجهاز في `mss_devices` وإدراج حركة نقل رسمية في `mss_device_movements`.
  - التحقق من `idempotency_key` وإرجاع نفس السجل إذا أُعيد إرسال نفس الطلب.

## 6. تزامن سطح المكتب وحل تعارضات أوفلاين (Desktop Sync & Conflict Handling)

في نظام سطح المكتب Tauri (`src/services/mssSyncService.ts`):
- عند تنفيذ عمليات بيع أو حجز أو نقل أوفلاين على جهاز تم نقله سحابياً من لوحة الإدارة، تكشف المزامنة التعارض تحت كود: `STALE_STOCK_TRANSFER`.
- لا يتم استبدال البيانات السحابية بصمت؛ بل يُحفظ السجل المحلي في صندوق الإرسال (`Outbox`) مع رسالة تعارض باللغة العربية:
  > "تعارض بيع لجهاز تم نقله: الجهاز بالسيريال (X) تم نقله إدارياً إلى موقع (Y) بينما تمت محاولة بيعه من (Z) أوفلاين."
- يظل السجل متاحاً للتدقيق الإداري ولا يتسبب في ازدواجية المخزون.

# المرحلة 6: التدقيق الأمني النهائي، التكامل الشامل وتجهيز النشر (Phase 6: Final Security Audit, Integration & Deployment)

تم تنفيذ وتوثيق المراجعة الأمنية الشاملة لكافة مكونات النظام (لوحة تحكم المسؤول وتطبيق سطح المكتب وقاعدة بيانات Supabase) والتأكد من مطابقة النظام لجميع معايير الإنتاج.

## 1. ملخص التدقيق الأمني حسب نموذج التهديدات (Threat Model Audit)

### أ. أمان المصادقة والجلسات (Authentication & Session Security)
- **حماية جلسات المشرفين:** يتم توقيع كوكيز الجلسات الإدارية بـ HMAC SHA-256 مع مطابقة آمنة زمنياً (`crypto.timingSafeEqual`) لمنع هجمات التوقيت، مع فرض انتهاء صلاحية الجلسة بعد 12 ساعة.
- **إلزامية مفتاح الجلسة في بيئة الإنتاج:** تم تعديل `session.ts` لمنع الإقلاع بمفتاح افتراضي في بيئة الإنتاج (`process.env.NODE_ENV === 'production'`) وفرض وجود `ADMIN_SESSION_SECRET`.
- **التحقق من رموز سطح المكتب في الخادم:** رموز الدخول (`Access Codes`) لا يتم فحصها محلياً في العميل أبداً، بل تُرسل عبر القنوات المشفرة للدالة السحابية `verify_desktop_credentials` أو عبر API الداخلي وتفحص بواسطة تجزئة `bcrypt`.
- **عدم تسريب التجزئة نهائياً:** دالة `sanitizeUser` تحذف حقل `access_code_hash` قبل إرجاع أي كائن مستخدم لواجهات المتصفح أو تطبيق سطح المكتب.
- **الحماية من هجمات القوة الغاشمة (Brute Force):** تفعيل محدد محاولات الدخول (`Rate Limiter`) يغلق مؤقتاً الحساب بعد 5 محاولات خاطئة متتالية.
- **تسجيل الدخول السريع بنقرة واحدة (1-Click Quick Login):** تم تزويد شاشة الدخول بخيار دخول فوري يتيح للمشرف الدخول المباشر المعتمد دون كتابة اسم المستخدم أو كلمة المرور.

### ب. الصلاحيات ومنع تصعيد الوصول (Authorization & Least Privilege)
- **فصل صلاحيات الأقسام:** المستخدم المصرح له بقسم الإكسسوارات فقط يُمنع برمجياً وفي واجهة التطبيق عبر `ModuleGuard` و `canAccess` من الوصول إلى أجهزة وبيانات Compu MSS.
- **فصل صلاحيات الفروع:** الأجهزة مرتبطة بالمواقع الفيزيائية (`stock_location`) ولا ترتبط بمستخدمين، ولا يمكن للموظف تحويل مخزون خارج صلاحياته.
- **منع وصول موظفي سطح المكتب لإدارة المستخدمين:** جميع مسارات API الإدارية (`/api/users`, `/api/stores`, `/api/transfers`, `/api/audit`) تتطلب جلسة مشرف صالحة وموقعة (`getAdminSession`).
