# Phase 4 — Fix and Verify Backup Destination Handling

This is a critical part of the task.

The user has selected this actual Windows directory:

`C:\Users\Administrator\Desktop\test backup`

Two backups were reportedly generated (one manual and one scheduled), but the expected files were not found inside the selected directory.

Investigate the actual root cause.

### A. Understand the runtime difference

The frontend may be running at:

`http://localhost:5173/`

Determine whether this is:

1. A normal browser session running Vite independently.
2. A Tauri desktop development session using the Vite development server.

These are not equivalent.

A normal browser session does not automatically have access to Tauri filesystem APIs or the Rust backend.

The backup destination functionality must be implemented through the Tauri desktop backend, using the appropriate Tauri v2 APIs and permissions.

If the application is being tested in a normal browser:

- Detect that Tauri APIs are unavailable.
- Display a clear explanation that filesystem backup operations require the desktop application.
- Do not display fake success messages.
- Do not pretend that a real backup file was created.
- Do not silently save a fictional destination path.

If running inside Tauri:

- Use the actual native folder picker.
- Use the actual selected absolute directory path.
- Perform backup file creation through the desktop backend.
- Return the actual resulting file paths to the frontend.

### B. Verify the exact selected directory

When the user selects:

`C:\Users\Administrator\Desktop\test backup`

The application must:

1. Preserve the actual selected absolute path.
2. Persist it correctly.
3. Pass that exact destination to the backend.
4. Create the backup file inside that directory.
5. Verify that the file exists.
6. Return the actual file path to the UI.
7. Record the actual file path in backup history.

Do not confuse the selected directory with the generated backup filename.

Do not display a destination path that differs from the actual write location.

### C. Multiple destination support

The user must be able to configure more than one backup destination.

For example:

- `C:\Users\Administrator\Desktop\test backup`
- `D:\MSS Backups`
- Another accessible folder.

When multiple destinations are configured, every backup operation must attempt to create a backup file in every configured destination.

This requirement applies to:

- Manual backups.
- Scheduled backups.
- Event-triggered backups, if enabled.

For every backup operation:

1. Read the currently saved destination list.
2. Validate each destination independently.
3. Generate the backup safely.
4. Write a valid backup file to each accessible destination.
5. Verify each generated file independently.
6. Record the actual result for each destination.

If one destination fails:

- Continue attempting the remaining destinations.
- Report which destination succeeded and which failed.
- Never report the entire operation as fully successful if one or more configured destinations failed.
- Preserve useful error details for the user.

Do not silently skip a destination.

### D. File creation and verification

For every destination, verify:

- The directory exists or is created only according to the existing intended behavior.
- The directory is writable.
- The backup file was actually created.
- The file size is greater than zero.
- The resulting path is the real absolute path.
- The backup file is a valid backup using the existing SQLite-safe backup mechanism.

Do not blindly copy an active SQLite database file if doing so could produce an inconsistent backup.

Do not record a successful backup before the file has been verified.

### E. Backup history and opening folders

Ensure that backup history records the actual resulting file paths.

If the UI provides an option to open the backup location:

- Open the real directory containing the backup.
- Use the actual recorded path.
- Do not construct a fake or guessed path.
- Show a clear error if the file or directory no longer exists.

- Backup history must show the actual files and timestamps.

8. Verify that its size is greater than zero.

10. Add a second destination.
11. Wait for another scheduled execution.
12. Verify that both destinations receive a new backup file.
13. Remove one destination and verify that subsequent backups use only the remaining configured destinations.
14. Restart the application and verify that the schedule and destination list persist.

Do not use a manual backup as proof that scheduled backups work. Test both independently.
