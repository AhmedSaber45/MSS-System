# Final Production Cleanup & Version Release – Compu MSS System v1.0.2

The development phase is complete. Prepare the entire application for its first clean production release by removing all dummy, demo, test, and development data from BOTH modules:

- Accessories
- Compu MSS

Also update the application version to **1.0.2** everywhere it is referenced, including the Admin Dashboard.

This is a comprehensive production cleanup, not a UI-only change.

Before making any deletion, inspect all data sources used by the application:

- Supabase database.
- Local SQLite database.
- Local Storage.
- Session Storage.
- IndexedDB, if used.
- Local synchronization queues and pending outbox records.
- Any other local persistence mechanism.

Identify all development, demo, placeholder, and test data created during development.

Inspect both modules independently and identify all related tables, relationships, foreign keys, and dependencies.

## 3. Remove All Existing Application Users

Remove all existing application users, including development accounts and test accounts.

Inspect both the authentication provider and any application-specific user tables.

Important requirements:

- If Supabase Auth is used, delete users through the supported Supabase Auth Admin API or a secure administrative script.
- Do NOT directly delete records from Supabase internal `auth` tables using ordinary SQL.
- Remove related user profiles, roles, permissions, and development-specific associations where appropriate.
- Remove local development user records and cached authentication state.
- Never expose the Supabase service-role key or administrative credentials in frontend code, desktop bundles, logs, or committed files.

### First Super Admin Bootstrap

Since all existing users will be deleted, prepare a secure procedure to create the first production Super Admin after cleanup.

- Do not create a fake default administrator.
- Do not hardcode credentials.
- Do not weaken authentication or authorization.
- Document the exact secure steps required to create the first Super Admin.
- Ensure the application can be accessed and initialized safely after the cleanup.
- Preserve all existing permission and role logic.

## 4. Local Data Cleanup

Clean the local application data as well:

- Remove development records from SQLite.

Ensure the application starts with a genuinely clean state after the reset.

## 5. Preserve the Database Schema and Application Structure

This is a data cleanup, NOT a database redesign.

- Preserve all existing production tables and their schemas.
- Preserve columns, indexes, constraints, foreign keys, triggers, functions, RLS policies, and permissions.
- Preserve essential application settings and configuration.
- Preserve the existing application architecture and module separation.
- Do not delete migrations or schema definitions.
- Do not remove real application features or business logic.
- Do not modify the Accessories/Compu MSS separation.
- Do not introduce dummy fallback data after cleanup.

The goal is an empty production-ready business database, not an empty or broken application.

## 6. Backup and Destructive Operation Safety

This cleanup is destructive and must be handled carefully.

Before deleting anything:

1. Identify the exact Supabase project and environment currently configured.
2. Identify the local SQLite database file and its actual location.
3. Generate a complete backup of the relevant database data.
4. Preserve the backup outside the databases being cleaned.
5. Report the number of records identified for deletion, grouped by module and data source.
6. Identify any records that cannot confidently be classified as development data.

Do not delete anything if the target database/environment is ambiguous or if the operation could unintentionally affect another project.

### Execution Requirements

- Prepare a controlled, repeatable cleanup procedure.
- Avoid placing destructive deletion logic in normal application startup.
- Do not automatically wipe data whenever the application launches.
- Make the cleanup a deliberate one-time release operation.
- Use dependency-aware deletion ordering and handle foreign keys correctly.
- Make the operation safe against partial execution and document recovery steps.

For Supabase:
- If database cleanup requires SQL, generate ONE complete, consolidated, safe SQL cleanup file.
- Include the exact file path.
- Verify the complete SQL against the actual existing schema and relationships.
- Make it ready for execution in the Supabase SQL Editor.
- Do not claim that the SQL has been executed.
- Handle Supabase Auth user deletion separately through the supported secure administrative process.

For local SQLite:
- Provide the appropriate verified cleanup script or migration procedure.
- Preserve the database schema.
- Ensure the correct database file is targeted.
