# COMPU MSS — LAPTOP GPU SPECIFICATION & ADMIN OPERATIONS MIGRATION

## MISSION

Implement two major improvements to the existing Compu MSS desktop application:

1. Add Graphics Card (GPU) information to laptop specifications throughout the Compu MSS catalog and related workflows.
2. Migrate the operational management capabilities currently available in the separate Admin Dashboard into the Compu MSS desktop application.

The goal is to make Compu MSS the primary interface for daily operational management while preserving the existing centralized security, database architecture, and business logic.

**IMPORTANT: This is a feature migration, NOT a page-copying exercise.**

Do not blindly copy Admin Dashboard pages into the desktop application.

Instead:

- If a feature already exists in Compu MSS, preserve it and add only the missing capabilities.
- If a feature partially exists, extend the existing implementation with the missing functionality.
- Only create a new desktop page when the corresponding functionality does not exist anywhere in Compu MSS.
- If a completely new page is required, implement it natively using the desktop application's existing design system and interaction patterns.
- After successful migration and verification, remove the relocated operational pages from Admin Dashboard.

Execute the task completely. Do not stop after the audit.

---

# PHASE 1 — PRE-IMPLEMENTATION AUDIT

Before changing anything:

- Read `AGENTS.md`, `rules.md`, `goals.md`, and all relevant documentation.
- Inspect the current Git status and preserve all valid uncommitted changes.
- Inspect the complete Compu MSS desktop module.
- Inspect the separate `admin-dashboard/` project.
- Understand the current Supabase schema, RLS policies, Edge Functions, authentication, permissions, SQLite integration, Outbox, and synchronization architecture.
- Inspect existing MSS pages, navigation, reusable components, hooks, services, and data models.
- Identify the current implementation of every Admin Dashboard section involved in this migration.
- Identify existing functionality in the desktop application that overlaps with the Admin Dashboard.

## 1.1 Mandatory Feature-by-Feature Comparison

Before implementation, create a detailed internal feature mapping for every relevant Admin Dashboard page.

For each page and its individual features, identify:

- Current Admin Dashboard page and file paths.
- Current desktop equivalent, if any.
- Features already implemented in Compu MSS.
- Features available only in Admin Dashboard.
- Features that exist in both but behave differently.
- Current database source and server-side operations.
- Required missing functionality.
- Existing components and services that can be reused.
- Security and permission requirements.
- Offline and synchronization requirements.
- Final destination inside Compu MSS.

Do not compare pages based on their names alone. Compare their actual functionality, workflows, actions, data, permissions, and business rules.

## 1.2 Mandatory Integration Decision Rules

Apply these rules to EVERY affected section.

### Case A — The entire functionality already exists in Compu MSS

- Keep the existing desktop implementation.
- Do not create another page.
- Do not duplicate existing features.
- Compare both implementations and identify any meaningful differences.
- Add only genuinely missing capabilities, if any.
- Preserve the existing desktop workflows and business logic.

### Case B — Compu MSS already has a page, but it is missing some Admin Dashboard features

This is the most important integration scenario.

- Use the existing Compu MSS page as the primary destination.
- Preserve all existing functionality, components, workflows, and valid business logic.
- Identify the exact features that are missing.
- Implement only those missing features inside the existing page.
- Extend existing components, forms, tables, filters, actions, and services where appropriate.
- Do not copy the Admin Dashboard page.
- Do not create a second page with overlapping functionality.
- Do not replace the existing desktop page with the Admin Dashboard implementation.
- Do not remove existing functionality just because the Admin Dashboard implementation handles something differently.

The final desktop page must combine the existing Compu MSS capabilities with the missing Admin Dashboard capabilities into one coherent experience.

### Case C — The corresponding functionality does not exist anywhere in Compu MSS

Only in this case:

- Create a new native desktop page or section.
- Migrate the required operational capabilities from the Admin Dashboard.
- Reimplement the functionality using the desktop application's architecture, components, navigation, and design system.
- Reuse existing services and authoritative server-side operations wherever possible.
- Do not embed the Admin Dashboard webpage or copy its layout as-is.
- Make the new section feel like a natural part of Compu MSS.

### Case D — A feature exists in both applications but has different behavior

- Investigate why the implementations differ.
- Identify which behavior is authoritative and consistent with the existing database and business rules.
- Preserve valid desktop behavior.
- Integrate missing capabilities without silently changing existing workflows.
- If the two implementations conflict, resolve the conflict based on the authoritative server-side logic and document the decision.
- Never create competing implementations of the same business operation.

## 1.3 Integration Principle

**The objective is to migrate capabilities, not pages.**

A page should only be created when no equivalent destination exists in Compu MSS.

A page should only be removed from Admin Dashboard after all of its required capabilities have been successfully integrated into Compu MSS and verified.

Do not make assumptions about table relationships or rewrite existing database structures without understanding their dependencies.

# PHASE 2 — ADD GPU TO LAPTOP SPECIFICATIONS

## 2.1 Catalog & Product Specifications

Add a Graphics Card (GPU) field to laptop specifications in Compu MSS.

Currently, laptop specifications already include information such as:

- Processor.
- RAM.
- Storage / SSD / HDD.
- Display / Screen.
- Other existing hardware specifications.

GPU must become a first-class specification alongside these fields.

Inspect the current product model and specification structure before choosing where to add it.

### GPU Information

Support useful GPU information such as:

- GPU manufacturer / brand.
- GPU model.
- GPU type, where applicable (Integrated or Dedicated).
- VRAM, when applicable and known.

Do not force unnecessary fields if the existing product specification design is simpler.

The GPU information must be optional because some devices may have unknown or unspecified graphics hardware.

Do not insert fake GPU values when information is missing.

## 2.2 All Relevant Workflows

Update every relevant part of Compu MSS where laptop specifications are created, edited, displayed, or used.

Inspect and update:

- Catalog product creation.
- Catalog product editing.
- Laptop specification forms.
- Product details.
- Product information views.
- Inventory device details, where specifications are displayed.
- Search and filtering, if specification-based search is supported.
- Relevant reports or exports, if they display laptop specifications.

Ensure the GPU field appears naturally alongside the existing CPU, RAM, storage, and display information.

Do not display GPU fields for unrelated product categories unless the existing specification architecture explicitly supports that behavior.

## 2.3 Database & Data Compatibility

If the existing schema needs modification:

- Preserve all existing product records.
- Make the GPU field nullable/optional.
- Preserve compatibility with existing devices that have no GPU information.
- Update TypeScript types, validation, database mapping, and serialization consistently.
- Preserve offline SQLite behavior and Supabase synchronization.
- Ensure old records continue to load correctly.
- Ensure records without GPU information do not cause validation or rendering errors.

If SQL changes are required:

Create ONE complete, consolidated, safe SQL migration file ready for Supabase SQL Editor.

- Include the exact file path.
- Verify the migration against the current schema.
- Preserve existing data and constraints.
- Do not execute the migration.
- Do not claim database changes have been applied.

# PHASE 3 — MIGRATE OPERATIONAL MANAGEMENT INTO COMPU MSS

The following operational capabilities currently exist in the separate Admin Dashboard and must become available inside the Compu MSS desktop application:

1. Stores & Warehouses.
2. Inventory Management.
3. Inventory Transfers.
4. Activity & Audit Log.

**Before creating any new desktop page, apply the integration decision rules from Phase 1.**

For every section:

- If an equivalent desktop page exists, extend it.
- If only some capabilities exist, add only the missing capabilities.
- If no equivalent functionality exists, create a new native desktop page.
- Never create duplicate pages or competing workflows.

## 3.1 Stores & Warehouses

Migrate the Stores & Warehouses management capabilities into Compu MSS.

The desktop application must support the existing administrative capabilities, including:

- View all stores and warehouses.
- Create a new store or warehouse.
- Edit existing details.
- Activate and deactivate locations.
- Archive locations where supported.
- Manage users assigned to locations.
- View warehouse memberships.
- Handle partner join/leave operations.
- Manage existing warehouse relationships.
- Perform supported warehouse merge workflows.

Preserve the distinction between users and warehouses.

A user is a login identity. A warehouse/store is an inventory location.

Do not link inventory ownership directly to a human user.

Preserve historical relationships and transaction records when users or partners change.

### Existing Location Management

If Compu MSS already has branch, store, or location management:

- Extend the existing implementation.
- Integrate the missing administrative operations into the existing interface.
- Preserve current location IDs and relationships.
- Preserve current inventory assignment behavior.
- Do not create a second location management system.
- Do not replace the existing branch-specific inventory model.

If no equivalent location management functionality exists, create a new native Stores & Warehouses section.

## 3.2 Inventory Management

Migrate the Admin Dashboard inventory management capabilities into Compu MSS.

Integrate them with the existing MSS inventory system.

The desktop interface should allow authorized users to:

- View inventory across available warehouses.
- Filter inventory by warehouse.
- Filter by product or device.
- Inspect serialized devices.
- View serial numbers and device status.
- View available, reserved, sold, damaged, or other supported statuses.
- View stock quantities and warehouse balances.
- Inspect relevant inventory history.

### Existing Inventory Integration

If the Compu MSS inventory page already provides some of these capabilities:

- Keep the existing inventory page.
- Preserve its current workflows and operations.
- Add only the missing warehouse-level management and inspection capabilities.
- Extend existing filters, tables, detail views, and actions.
- Avoid creating another inventory page.

Where existing MSS inventory pages already provide these capabilities, extend those pages instead of creating duplicates.

The existing branch-specific inventory model must remain intact.

Do not replace the current inventory system with a simplified global stock counter.

## 3.3 Inventory Transfers

Migrate the inventory transfer functionality from the Admin Dashboard into Compu MSS.

Integrate it with existing inventory movements and transfer-related workflows.

Support the existing transfer capabilities:

- Transfer an individual serialized device.
- Transfer multiple selected devices.
- Transfer eligible inventory for a product.
- Transfer all eligible inventory from a source warehouse to a destination warehouse, where supported.
- Preview the transfer before confirmation.
- Display the source and destination locations.
- Display affected devices and quantities.
- Show the final transfer result.
- Display transfer history and status.

### Existing Movements Integration

Before creating a new Inventory Transfers page:

- Inspect the existing Movements section.
- Determine whether it already supports transfers or transfer-related operations.
- If it does, extend that section to support the complete required transfer workflow.
- Integrate transfer history into the existing movement history where appropriate.
- Do not create a second transfer mechanism or duplicate transfer history.
- If no suitable existing section exists, create a dedicated native Inventory Transfers page.

### Transfer Safety

Preserve all existing transfer safety rules:

- Transfers must be atomic.
- Transfers must be idempotent.
- Prevent duplicate device/location assignments.
- Recheck device eligibility before executing a transfer.
- Exclude sold, reserved, damaged, pending, or otherwise ineligible items unless an explicitly supported workflow allows them.
- Preserve serial numbers, original device IDs, purchase costs, purchase dates, reservations, and historical records.
- Do not create fake sales, purchases, revenue, or profit.
- Do not silently overwrite concurrent inventory changes.

Preserve the current synchronization and conflict-resolution behavior.

Do not implement a separate desktop-only transfer mechanism that bypasses the existing authoritative transfer logic.

The desktop application should call the appropriate secure existing server-side operations.

## 3.4 Activity & Audit Log

Migrate the Activity & Audit Log functionality into Compu MSS.

The desktop application must provide an appropriate interface for reviewing administrative and operational events.

Include relevant events such as:

- User creation and modification.
- User activation and deactivation.
- Access-code changes.
- Permission changes.
- Warehouse creation and modification.
- Warehouse membership changes.
- Warehouse merges.
- Inventory movements.
- Inventory transfers.
- Other important administrative operations.

Display available information such as:

- Actor.
- Action.
- Target entity.
- Timestamp.
- Relevant metadata.
- Result/status, where available.

Add useful filtering and search capabilities where supported.

### Existing History Integration

Before creating a new Activity & Audit Log page:

- Inspect the existing History section and any other operational activity views.
- Determine whether the existing page can accommodate the required events.
- If it can, extend it and introduce clear filtering or categorization for operational versus administrative/security events.
- If its data model or purpose is fundamentally different, keep the existing History functionality intact and create a separate Audit Log section only when necessary.
- Avoid duplicate event listings and competing history systems.

### Audit Integrity

- Preserve the existing audit log data.
- Do not recreate historical records.
- Do not change historical actor identities.
- Do not expose access codes, tokens, or other secrets.
- Do not allow ordinary users to edit or delete audit records.
- Preserve the existing database-side audit generation and security controls.

Clearly distinguish operational history from security/admin audit events when their data models serve different purposes.

# PHASE 5 — PERMISSIONS & ADMIN DASHBOARD RESPONSIBILITIES

Moving operational capabilities does not mean removing the security architecture established previously.

The Admin Dashboard remains a separate administrative application.

Its remaining responsibilities should include functionality that is not being moved, such as:

- Admin account and access management.
- Desktop user creation and management.
- Access-code management.
- Module permissions.
- Other system-level settings that are intentionally admin-only.

## 5.1 Authorization

Review the existing permission model before implementing navigation and operations.

Ensure:

- Only authorized users can access sensitive management actions.
- Users cannot grant themselves permissions.
- Warehouse membership restrictions are enforced.
- Inventory transfers are authorized server-side.
- Audit log access follows the appropriate permissions.
- Hiding a sidebar item is never treated as sufficient security.
- Existing module permissions remain enforced.
- Existing admin-only operations remain protected.
- The desktop app uses the same authoritative authorization rules as the Admin Dashboard.

If the current permission model does not distinguish read and write operations for these features, document the limitation and implement the safest compatible approach without introducing an inconsistent permission system.

Do not weaken Supabase RLS or Edge Function authorization to make the desktop UI work.

## 5.2 Shared Security Architecture

The migration must not create a second security or authorization system.

- Reuse existing authentication and authorization mechanisms.
- Preserve existing user identities.
- Preserve server-side validation.
- Preserve existing Edge Functions and database security controls.
- Do not expose Supabase service-role credentials in the frontend or Tauri application.
- Do not move privileged database operations into client-side code.
- Do not make sensitive operations directly writable by ordinary desktop clients.
- Preserve existing audit generation and access restrictions.

# PHASE 7 — OFFLINE SUPPORT & SYNCHRONIZATION

This is critical because Compu MSS already uses an offline-first architecture.

Inspect the current SQLite, Outbox, synchronization, and conflict-resolution implementation.

For every new or extended workflow, determine whether it can safely operate offline.

Requirements:

- Preserve pending Outbox operations.
- Preserve existing offline functionality.
- Do not silently discard unsynchronized data.
- Do not duplicate operations after reconnection.
- Do not allow operations to synchronize under another user's identity.
- Handle stale warehouse data safely.
- Handle transfer conflicts safely.
- Refresh authoritative cloud data after reconnection.
- Keep local data consistent with confirmed server-side changes.
- Preserve existing synchronization identifiers and idempotency behavior.

For operations that require an online server-side transaction:

- Clearly communicate that requirement in the UI.
- Disable or prevent unsafe execution while offline.
- Do not pretend that the operation succeeded offline.
- Do not create a local success record that falsely represents a confirmed server-side transaction.
- Refresh the local state only after the authoritative operation is confirmed.

Do not invent an offline transfer success state when the authoritative server operation has not completed.
